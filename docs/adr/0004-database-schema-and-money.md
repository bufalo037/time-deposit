# 0004. Database schema: snake_case names, cent-precision money, no plan-type constraint

## Status
Accepted (2026-11-25)

## Context
README "Database Setup" defines `timeDeposits(id, planType, days, balance)` and
`withdrawals(id, timeDepositId, amount, date)`, with Integer ids, required columns and Decimal money. Three things
are left open:
- naming: PostgreSQL folds unquoted identifiers to lower case, so `timeDeposits` would become `timedeposits`
- money precision: `TimeDeposit.balance` is a `double`, and `updateBalance` produces values like
  `1000.9300000000001` (pinned by the characterization tests)
- whether the database should restrict plan types

## Decision
Schema in `V1__create_time_deposits_and_withdrawals.sql`:

- **Names:** snake_case tables and columns (`time_deposits.plan_type`, `withdrawals.time_deposit_id`). JPA entities
  and the API keep the README's camelCase.
- **Ids:** `integer GENERATED BY DEFAULT AS IDENTITY`. `integer` matches `TimeDeposit`'s `int id`, and `BY DEFAULT`
  allows explicit ids in seed data.
- **Money:** `numeric(19,2)` for `balance` and `amount`: an exact decimal at cent precision. The persistence
  adapter converts the calculator's `double` with `BigDecimal.valueOf(d).setScale(2, HALF_UP)`.
  - *Assumption:* storing cents is the intended banking semantics. Double artifacts (`…0000001`) are representation
    error, not money, so they're removed at the storage boundary. The next update then starts from a clean cent
    amount. The calculation itself (`updateBalance`) is unchanged.
  - `BigDecimal.valueOf` (the decimal the double represents) is used, not `new BigDecimal(double)` (its exact
    binary value). For example, `1004.165` is stored as `1004.17`, not `1004.16`. Tests pin this.
- **Constraints:** `NOT NULL` on every README-required column, named primary keys, the named foreign key
  `fk_withdrawals_time_deposits`, and an index on `withdrawals.time_deposit_id` (PostgreSQL doesn't index foreign
  keys automatically).
- **No `CHECK` on `plan_type`:** new plans must not require a schema change (README extensibility). The calculator
  already gives unknown plans no interest, and the README says invalid input handling isn't required.
- `withdrawals.date` keeps the README name. `date` is a non-reserved keyword in PostgreSQL.
- *Assumption:* withdrawals are historical records. `balance` is the current balance, and withdrawals don't affect
  interest, because the README defines interest only by plan type and days.

## Consequences
- The schema reads naturally in SQL, and the mapping to camelCase is explicit in the entities.
- Stored money is exact and never shows double artifacts. In-memory results and stored values can differ by less
  than a cent, by design.
- Adding a plan type is a pure code change (a new interest policy), with no migration.
- Rejected: quoted camelCase identifiers (must be quoted in every statement, error-prone); unscaled `numeric`
  (artifacts would persist and compound); `double precision` (contradicts README "Decimal", imprecise for money); a
  `CHECK` constraint on plan types (couples every new plan to a migration).
